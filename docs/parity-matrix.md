# Parity matrix

Status of Python → Rust node parity. This matrix is the Gate 0 artifact from
[`docs/rust-reconciliation-plan.md`](rust-reconciliation-plan.md) §3 and is
also the acceptance tracker for
[`docs/node-hermes-parity.md`](node-hermes-parity.md) §15–§16.

**Rule:** no row is marked `green` from code inspection alone. A green row must
name an automated test (or command) that asserts the behavior in this checkout
and that passed. A fixture assertion is not a live Python comparison; rows that
only compare against the checked-in baseline stay at most `partial` unless the
row itself is the Rust behavior under test.

## Status legend

| Status | Meaning |
|---|---|
| `green` | A checked-in test asserts the behavior and the evidence command passed. |
| `partial` | Part of the behavior is asserted; a required part is missing, unwired, or only compared against a hand-written baseline. |
| `not-run` | The behavior may exist, but this Phase 0 run did not execute its gate (external environment, controller pytest, demo, clean host). |
| `not-implemented` | The Rust path does not exist yet. Tests may assert that the surface honestly reports absence. |

## Optional / post-Gate-2 gaps

- Native WebRTC (`webrtc-rs`/`str0m`) is not implemented. `/webrtc/offer` and
  `/webrtc/bitrate` run through a supervised external GStreamer helper; the
  worker now reuses the payload types in the peer's offer, and both bitrate and
  audio are acknowledged/applied by the checked-in worker. A GStreamer peer, a
  default headless Chromium 145 peer, Playwright Firefox 159.0 with OpenH264
  2.6.0, and Chromium 159 iPhone emulation completed ICE/DTLS through the
  controller proxy and decoded video/audio, including the dashboard KVM modal
  (`docs/gate2-live-controller-webrtc-report.md`,
  `docs/gate2-live-webrtc-matrix-report.md`). This is still host-candidate only
  (no STUN/TURN/trickle), same-host, and helper-first; Safari/WebKit, a distinct
  `srflx`/relay candidate, NAT, late-candidate trickle, multi-peer, and
  reconnect are unvalidated. The external helper still owns the session
  lifecycle, so a peer that closes while `appsrc` pushes still succeed can leave
  a session/encoder alive. No live helper/controller negotiation is run in CI.
- Controller display snapshots are implemented as a one-shot
  `GET /display/snapshot` (real JPEG from the configured capture source) with
  `GET /display/info` and a guarded typed 501 `GET /display/mjpeg`. Snapshot,
  info, hints, node status, `/agent/metrics`, and the audio discovery/sweep
  stubs are merged after the bearer guard so the unmodified controller works
  with `--api-token`; control routes remain guarded. A live disposable QMP node
  served a real 720x400 snapshot through the controller, and the full-mode
  dashboard rendered it; this is not in CI.
- Controller node-token propagation: the persistent per-node store, an
  `api_token` supplied in direct registration, or the global
  `OZMA_NODE_API_TOKEN` is sent as `Authorization: Bearer ...` by the snapshot,
  hints, metrics, power, codec, WebRTC, input and audio API proxies, and by
  direct background clients outside `api.py`: control-surface power, agent
  hints, soft-node stream snapshot/input/codec, terminal snapshots, serial
  polling, node RGB zones, mesh status, session init, and backup proxy.
  Resolution and header construction are centralized in
  `controller/node_auth.py`; precedence is persistent store → registration →
  global fallback. Tokens are not serialized in node JSON, events, dashboard
  responses, token metadata, or logs. Covered by fake-node HTTP suites
  (`tests/unit/controller/test_node_api_token_proxy.py`,
  `tests/unit/controller/test_node_api_token_direct.py`, and
  `tests/unit/controller/test_node_token_store.py`) asserting header
  present/absent, per-node over global, 401/403 handling, reload persistence,
  rotation/revocation, atomic `0600` writes, and token-free logs/responses; not
  yet exercised against a live token-protected Rust node.
  The node's public read-only routes (`/display/snapshot`, `/display/info`,
  `/ui/hints`, `/node/status`, `/agent/metrics`, `/audio/nodes`,
  `/audio/sweep`) remain readable without a token by design. The store is
  `node_tokens.json` (default next to the controller; `OZMA_NODE_TOKEN_STORE`
  overrides), written atomically with mode `0600` but **cleartext at rest**.
  `GET /api/v1/nodes/{node_id}/token` returns metadata only;
  `PUT` sets a supplied token without echoing it, or generates one and returns
  it once (`token_returned_once:true`); `DELETE` revokes it with a persistent
  tombstone (a re-registration cannot re-adopt it) and falls back to the global
  token if configured. GET needs `read`, PUT/DELETE need
  `write`/`admin`. Rotation updates `NodeInfo.api_token` and live soft-node
  streams, but the node itself must be reconfigured out-of-band. Direct
  registration and rotation still carry the token in cleartext over HTTP, so
  loopback/TLS/SSH tunneling is required; direct registration still has no token
  field. The dashboard now has a metadata-only node-token dialog (status,
  source, updated_at, revoked, and boolean global-fallback state) with
  generate/rotate and confirm-to-revoke. A generated token is shown once in a
  temporary reveal field with a warning; dismissing it clears the value from
  the DOM, and the UI never writes it to browser storage, console, or later
  requests. Covered by `tests/unit/controller/test_dashboard_node_token_ui.py`
  (headless Chromium against a fake controller). External device/peer endpoints
  (Sunshine, motion controllers, OLED/e-ink/LCD drivers, controller peers,
  sharing, WireGuard) are not node APIs and never receive the node token.
- Live-controller HLS proxy run: a Rust node's playlist and segment were proxied
  by the unmodified controller; the controller segment matched the node segment
  byte-for-byte and probed as H.264 720x400. The controller's `/codec` route was
  reachable after a route-order fix but at that time still did not proxy
  `hls-remote` streams to the node (GET reported controller-local encoders; POST
  was a typed 404). The controller now proxies `GET` and `POST
  /api/v1/streams/{id}/codec` for `hls-remote` streams to the node's `/codec`
  when the stream has a node API endpoint, returning the node's JSON and typed
  400/502 bodies unchanged; a transport failure or timeout is a controller 502.
  Non-remote captures keep the controller-local behavior. This proxy is covered
  by a fake-node HTTP suite (`tests/unit/controller/test_stream_codec_proxy.py`)
  and was repeated live through the controller against a real Rust node (software
  H.264 POST returned `applied:true`, `pending_restart:false`, restarted HLS,
  and the next segment probed as H.264); controller codec stats/probe DB and
  the node's encoder registry remain separate sources.
- Runtime codec override (`POST /codec`) validates and stores an
  `EncoderOverride` plus `OverrideReceipt`, and restarts a running HLS
  `HlsPipeline` with the mapped encoder. Software (`libx264`, `libx265`,
  `libsvtav1`, `libaom-av1`, `mjpeg`) and H.264/HEVC hardware
  (`vaapi`/`nvenc`/`qsv`/`v4l2m2m`) are supported; `applied: true` means that
  restart succeeded. Hardware availability is evidence from an injectable
  `EncoderProbe` (production runs bounded `ffmpeg -encoders` once), and a
  missing VAAPI render node is a typed error with remediation. A hardware
  request never silently becomes software: an explicit
  `allow_software_fallback` produces `fallback: true` with the requested and
  applied encoders, otherwise the result is a typed 502 and the previous
  pipeline is restored. With HLS off — or for a failed restart — the honest
  result remains `applied: false` / `pending_restart: true` (or a typed 502).
  Hardware AV1/MJPEG, `videotoolbox`, and WebRTC codec switching are not
  implemented; WebRTC keeps its existing encoder. No real GPU/ffmpeg hardware
  encode runs in CI, so driver-specific behaviour (VAAPI upload, NVENC/QSV
  rate control, V4L2M2M device open) still needs opt-in hardware validation.
  Audio routing (`/audio/*`) is wired to a real `AudioRouter` when
  `--audio-router pipewire|pulseaudio` is set, but there is no native DSP/room
  correction, no PipeWire node enumeration for `GET /audio/nodes`, and no
  `POST /audio/sweep` implementation; both return public typed 501 stubs with
  the soft-node response shape. There is no live audio-server run in CI.
  Per-VM sink creation belongs to `ozma-softnode --provision-audio`;
  `ozma-node` only receives the sink name.
  Without a router both still answer typed 501s/503s rather than fake success.
- D-Bus framebuffer display provider is implemented and selectable on the VM
  profile. It was live-validated against QEMU 11.1.3 (2D `Scanout`/`Update`,
  GL `ScanoutDMABUF`/`ScanoutDMABUF2`/`UpdateDMABUF`, and GL-path `Disable`,
  including a node HLS run over the shared QMP connection) on 2026-11-24. The
  GL follow-up maps linear XBGR/ABGR/XRGB/ARGB/BGRA/RGBA and multi-plane
  NV12/NV21/YUV420/YVU420 DMA-BUFs, issues `DMA_BUF_IOCTL_SYNC` around CPU
  reads, applies only the damaged rectangle on `UpdateDMABUF`, verifies
  `y0_top` orientation, and produced real 1280x800 HLS/snapshot frames with the
  live v2 message. Named packed-32-bit tiled modifiers have a GBM/EGL
  readback; AMD DCC is imported when `ScanoutDMABUF2` supplies the main +
  metadata planes, while Intel CCS and tiled YUV return typed errors naming the
  modifier and fourcc. This host exported only linear or `DRM_FORMAT_MOD_INVALID`
  buffers. This path is not in CI: the real test is `#[ignore]`, gated by
  `OZMA_DBUS_TEST_QMP`, and needs an exclusive QMP socket. Remaining limits:
  no live named-tiled/DCC scanout source on this host, no tiled-YUV colour
  conversion/readback, the initial all-black GL
  scanout is held for at most 750 ms before a genuinely black screen is
  served, and a stalled `next_frame` consumer back-pressures QEMU. The HLS
  pipeline restarts ffmpeg on a dynamic frame-size change (append-list +
  discontinuity); the GL follow-up observed 720x400 -> 1280x800 scanouts after
  reset and ignores a stale oversized `UpdateDMABUF` until the next scanout.
  The ffmpeg VNC path remains a transition path: unauthenticated loopback VNC
  only, scaled output, no VNC audio/input, and no live VNC validation in CI.
- `ozma-softnode` provisioning: libvirt API/device creation beyond the
  `qemu:commandline` block, validating that QEMU opened/grabbed created evdev
  devices, audible/non-silent sink validation, native PipeWire node creation,
  live supervisor-restart validation against a real audio server/sink, USB/media,

  optional bounded child `/api/v1/connection` polling (`--child-poll-interval-ms`,
  timeout/stale/token-free summaries), opt-in QMP/display XML injection, env/evdev
